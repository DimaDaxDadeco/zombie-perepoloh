# Архитектура

## Слои

```
main.js                 точка входа
  └── core/game.js      оркестратор: цикл, состояния, экраны
        ├── core/round.js       симуляция мира (герой, зомби, снаряды)
        ├── screens/*           DOM-оверлеи и HUD
        ├── core/audio.js       звук
        ├── core/input.js       клавиатура и геймпад (см. input.md)
        ├── core/storage.js     сохранение
        ├── core/upgrades.js    бонусы героя на старте раунда (чистая арифметика)
        └── core/campaign.js    сюжетные главы: какие пройдены и какая открыта

test/*                  прогон раунда в Node, без браузера (см. balance.md)
```

Главное разделение: **`Round` ничего не знает про экраны и меню**, а `Game`
ничего не знает про то, как зомби ходят. Связь односторонняя — `Round` сообщает
о событиях колбэками, которые ему передал `Game`.

### Второе разделение: логика не трогает DOM

`Round`, `entities/*`, `systems/*` и `weapons/*` не обращаются к `document`,
`window` или `canvas` ни разу. Рисование отделено по сигнатурам: `update(dt,
directions)` не знает про `ctx`, а `draw(ctx)` получает контекст параметром —
`render/background.js` и `render/sprites.js` тоже чистые функции.

Изначально это было следствием опрятности, а теперь на этом стоит автотест:
раунд поднимается в Node напрямую, минуя `Game`, canvas и экраны, и вся
балансная сетка укладывается в 18 секунд. **Не заводите DOM в этих слоях** —
сломается не стиль, а проверка.

**Сценарий раунда живёт в объекте-цели** (`systems/goal.js`), а не в `Round`.
Раньше `updateBossPhase` совмещал таймер, спавн и условие победы; с четырьмя
видами задач он превратился бы в лестницу условий. Теперь развилка одна — что
происходит, когда таймер добежал до нуля, — а цель только читает мир и
отвечает «выполнено или нет». Победу по-прежнему объявляет `Round.finish`:
если бы цель заканчивала раунд сама, исход перестал бы приходить в `onVictory`,
и автотест считал бы пройденную главу проигранной.

Из того же соображения `getUpgrades` и `applyCard` переехали из `Game` в
`core/upgrades.js` и `systems/levelup.js`: тест обязан считать бонусы и
применять карточки ТЕМ ЖЕ кодом, что и игра. Своя копия формулы в тесте
означала бы, что он меряет игру, которой нет.

## Игровой цикл

`Game.loop()` вызывается через `requestAnimationFrame`. Дельта времени
ограничена сверху (`MAX_FRAME_DELTA = 0.05`), иначе после сворачивания окна
один кадр «перепрыгнул» бы несколько секунд симуляции.

```
loop(timestamp)
  ├── update(dt)   обновляет только то, что активно в текущем состоянии
  └── draw()       рисует мир, затем HUD
```

## Машина состояний

```
        ┌──────► MENU ◄──────────────────┐
        │          │ Новая игра          │ В меню
        │          ▼                     │
        │      PLAYERS                   │  (только в цепочке новой игры)
        │          ▼                     │
        │     DIFFICULTY                 │
        │          ▼                     │
        │     CHARACTERS ─► WEAPONS      │
        │          │                     │
        │       PLAYING ◄──┐             │
        │        │  │      │ Продолжить  │
        │        │  └──► PAUSED ─────────┤
        │        │                       │
        │        ├──► CARDS ──► PLAYING  │  (новый уровень)
        │        │                       │
        │        ▼                       │
        │    ROUND_END ──────────────────┘  (победа или «почти получилось»)
        │        │ дальше
        │        ▼
        └───── SHOP  ──► PLAYING (следующий раунд) или MENU
```

«Продолжить» ведёт из `MENU` сразу в `PLAYING`: сложность, герой и оружие уже
лежат в сохранении.

Ввод разбирается в `Game.routeInput()` — единственном месте, где нажатия
превращаются в действия. Куда пойдёт кнопка, решает состояние игры, а не то,
чем её нажали; подробности — в [input.md](input.md).

Состояние хранится в `Game.state` (значения — `GameState`). `update()` работает
только в `PLAYING`; в `ROUND_END` дополнительно живут частицы салюта.

## Round как объект «мира»

Сущности и оружие получают `Round` под именем `world` и работают только через
его публичное API — это единственная точка, через которую они влияют на игру:

| Метод | Кто вызывает |
|---|---|
| `addProjectile(p)` | оружие при выстреле |
| `addEnemy(e)` | спавнер |
| `findNearestEnemy(x, y, opts)` | оружие для авто-прицела, ракета для наведения |
| `damageEnemy(enemy, amount, source)` | оружие прямого действия (молния, вертушка); `source` — `'weapon'` по умолчанию, `'ability'` или `'enemy'` |
| `explode(x, y, radius, damage, kind)` | помидор и ракета |
| `collectPickup(pickup)` | пикап, долетевший до героя |
| `onPlayerHurt()` / `onPlayerHealed()` | столкновения и регенерация |
| `useAbility()` | `Game` по нажатию пробела |

`Round` получает уровень сложности отдельным полем конструктора
(`difficulty`) и держит его в `this.difficultySpec` — не `difficulty`: у
`Spawner` так уже называется кривая по номеру раунда.

Благодаря этому оружие не импортирует ни зомби, ни частицы — его можно
добавлять, не трогая остальной код.

## Порядок обновления кадра

Кадр начинается с ввода — `poll()` → `routeInput()` → `endFrame()`, и только
потом `update(dt)`. Почему именно в таком порядке — в [input.md](input.md).

Порядок в `Round.update()` важен:

1. фаза раунда и спавн зомби;
2. герой (таймеры и способность, затем движение и оружие);
3. зомби (кроме момента появления босса — см. ниже), снаряды, пикапы;
4. расталкивание зомби между собой;
5. попадания снарядов, затем урон по герою;
6. частицы;
7. удаление «мёртвых» объектов одним проходом фильтрации.

Удаление вынесено в конец, чтобы никто не итерировался по массиву, из которого
одновременно что-то вырезают.

**Пауза на появление босса.** Пока идёт `Round.freezeTimer`, шаги 3 (зомби) и 5
(урон по герою) пропускаются: зомби замирают и не могут ударить. Расталкивание
(шаг 4) продолжает работать — иначе замершая толпа слиплась бы в одну точку.
Герой и его оружие не замирают никогда.

## Отрисовка

Мир рисуется на `<canvas>`, интерфейс — обычным DOM поверх него. Причина
простая: делать крупные кнопки, сетки и анимации кнопок в CSS проще и надёжнее,
чем изобретать вёрстку внутри canvas. HUD (сердечки, шкала, счётчики) —
исключение: он рисуется на canvas, потому что должен обновляться каждый кадр.

Персонажи сортируются по координате Y, чтобы тот, кто ниже, перекрывал того, кто
выше — дешёвый способ получить ощущение глубины.

Canvas масштабируется под `devicePixelRatio`, поэтому на ретине картинка резкая.

**Тряска экрана.** `Round.draw()` оборачивает всю отрисовку мира в
`save()`/`restore()` и в начале сдвигает контекст на затухающее случайное
смещение (`applyShake`). Поскольку HUD рисуется позже и уже в `game.js`,
интерфейс не трясётся — дрожит только мир. Это осознанно: прыгающие сердечки
читались бы как поломка.

**Частицы** (`systems/particles.js`) хранятся отдельными массивами по видам
(конфетти, кольца, молнии, взмахи, появления боссов). Каждый вид добавляется
своим методом `add*`, живёт по таймеру `life` и удаляется фильтрацией в
`update()`. Эффекты появления боссов рисуются раньше персонажей, чтобы босс
выходил «из» эффекта, а не поверх него.

## Отладка

`window.game` даёт доступ к экземпляру игры из консоли браузера:

```js
game.startRound(8)          // сразу восьмой раунд
game.storage.data.coins = 500
game.openShop('menu')
```
